## Context

Dashboard 当前以浅色玻璃卡片为主要视觉语言，但主题初始化会读取旧的暗色偏好并给根节点添加 `dark` class。现有组件大量使用浅色背景和固定深色文字，因此该状态会产生不可读组合。系统的数据存储已统一使用 `data/db/etf_data.db`，但尚无用户真实投入记录，模拟结果也不能代表实际执行。

## Goals / Non-Goals

**Goals:**

- 保留当前浅色视觉设计，并在刷新和路由切换后保持一致可读。
- 持久化记录用户实际追加投入的日期、金额和备注。
- 持久化每次投入在白酒、银行、红利、沪深300、科创50和国债之间的分项金额。
- 提供最近一次投入、累计投入、记录次数和按日期倒序的历史明细。
- 允许补录以往投入并删除误录记录。
- 保持模拟与真实执行记录明确分离。
- 移除与本月概览重叠的独立持仓模拟前端页面。

**Non-Goals:**

- 不重做 Dashboard 的颜色、卡片或排版体系。
- 不提供银行流水、券商账单或 CSV 自动解析。
- 不根据模拟计算自动写入真实投入。
- 不把投入记录纳入策略因子、评分或回测。

## Decisions

1. **统一锁定浅色主题。** 应用启动时显式应用 `light`，覆盖旧 `etf-mode=dark` 偏好。相比为所有历史硬编码颜色补齐暗色变体，该方案风险更低，也符合用户要求保留原设计。
2. **投入记录存入现有 SQLite。** 主表 `investment_record` 使用自增 ID、ISO 日期、整数分总额、备注和创建时间；子表 `investment_record_item` 以记录 ID 和资产名为联合主键保存六项整数分金额。整数分避免浮点累计误差；主子表允许旧的纯总额记录继续读取。
3. **API 由明细推导总额。** `POST /api/investments` 接收六个允许资产的分项金额，拒绝未知资产、负数和全零明细，并以分项合计生成总额；`GET /api/investments` 在每条记录中返回 allocations；`DELETE /api/investments/{id}` 级联删除明细。相同日期、总额和备注视为重复并返回冲突，延续已有防双击规则。
4. **手动确认真实投入。** 资金记录页提供历史日期、金额和备注表单。月度配置计算不自动写记录，因为计算结果不等于实际买入。
5. **沿用现有组件语言。** 新页面使用 NavBar、GlassCard、现有紫色主按钮和响应式布局，不引入新的视觉系统。
6. **删除重复模拟入口。** 前端移除 `Simulator` 页面和导航项；旧 `/simulator` 链接重定向到本月概览，后端计算接口保留给现有概览流程使用。

## Risks / Trade-offs

- [精确重复投入可能被当成误操作] → 用户可通过不同备注区分同日同额的两次真实投入。
- [本地 SQLite 只适合单用户本机使用] → 当前项目即为本地个人工具；未来多用户化时再增加账户维度。
- [强制浅色会暂时失去暗色模式] → 当前暗色模式本就不完整且不可用；待所有组件完成主题令牌化后再单独恢复。
- [手动录入可能与真实交易不一致] → 页面明确标注为用户确认的投入记录，不由模拟结果自动生成。
- [旧记录没有资产明细] → 保留并展示旧总额，同时标注“未记录分项”，不猜测历史分配。

## Migration Plan

1. 通过现有 `create_tables` 幂等创建 `investment_record` 表和索引。
2. 启动 API 时自动完成 schema 迁移，已有数据库和配置数据不受影响。
3. 发布前运行 API、前端单元测试和真实页面回归。
4. 回滚时可移除页面和 API；保留表不会影响现有策略流程。
